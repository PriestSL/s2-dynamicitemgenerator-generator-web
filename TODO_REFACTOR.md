## Мета

Отримати фронтенд на TypeScript із простим володінням даними, надійним редагуванням, порівнянням із базовим пресетом і перевірюваним локальним шляхом:

**Defaults або JSON → редагування → порівняння / reset → JSON / CFG / ZIP.**

Рефакторинг має усунути зайві залежності й дублювання, а не лише рознести наявні класи по нових файлах.

## Межі та робочі рішення

- Повний перехід власного коду фронтенду на TypeScript із strict-перевіркою типів — погоджена вимога від 6 жовтня 2026 року. Змішаний JS/TS допустимий лише між етапами; Vite залишається.
- Один власник даних редактора: незалежні `baseConfig` і `config`, окремо невеликий `view` та метадані документа.
- `baseConfig` — незмінний знімок вибраної бази; `config` — поточні зміни. Це не потребує state-management бібліотеки чи localStorage.
- Bootstrap залишається початковою основою. Остаточний вибір оформлення — після перевірки одного показового екрана; міграція UI-бібліотеки не є автоматично погодженим завданням.
- Поточний формат повного JSON зберігається на першому етапі. Diff-only, master/product і новий формат серверних пресетів не впроваджуються разом із цим рефакторингом.
- Бекенд і поведінку мережевої взаємодії зараз не змінюємо: endpoints, payload, серверний CRUD пресетів, PIN та пакування PAK поза обсягом функціональних змін. Фронтенд-код REST/PresetsManager і виклику PAK входить до TS-міграції зі збереженням цих контрактів.
- Зберігаємо сумісні точки входу для наявних інтеграцій. AppState-фасад можна тимчасово залишити, якщо він потрібний незмінюваним споживачам.
- Виправлення спільного генератора CFG можуть змінити майбутній вміст PAK, але не потребують зміни REST-контракту. Локальні перевірки не вважаються перевіркою серверного пакування чи гри.
- Не переписуємо defaults та ігрові правила без конкретної причини. Наявні defaults не називаємо vanilla без окремої перевірки.

### Повне охоплення TypeScript

| Етап | Обов'язковий обсяг TS |
| --- | --- |
| 1 | Контракти, defaults, створення незалежних baseConfig/config, числові правила; JS-фасад тимчасовий |
| 2 | Редагування, runtime-валідація JSON, імпорт/експорт конфігурації та AppState-фасад |
| 3 | Увесь генератор CFG, ZIP, файлове читання/завантаження та сумісні точки виклику генератора |
| 4 | Порівняння, reset і метадані документа |
| 5 | Увесь UI: app/bootstrap, контролери, renderer-и, події, поля, діалоги та UI helpers; показовий екран не обмежує обсяг TS лише одним екраном |
| 6 | Нова або змінена логіка доступності й адаптивної поведінки також на TS |
| 7 | Решта фронтенд-інтеграцій REST/PresetsManager/PAK, тести/helpers, допоміжні скрипти й виконувані конфігурації інструментів; остаточна перевірка повноти |

Тести й helpers переносити разом із відповідними модулями; етап 7 закриває залишок. У фіналі власних вихідних `.js`/`.mjs`/`.cjs` не лишається, включно з сумісними фасадами. Виконувані конфігурації інструментів перевести на підтримуваний TS-формат і включити в typecheck (за потреби окремий tsconfig). HTML, CSS/SCSS, JSON, CFG, зображення, сторонні залежності й згенерований JS збірки не є об'єктами мовної міграції. Сумісність інтеграцій забезпечити типізованими фасадами та налаштуванням збірки.

Ця вимога уточнює кінцевий результат, але не скасовує ручного рев'ю та окремого погодження наступного етапу.

## Контрольні точки ручного рев'ю
