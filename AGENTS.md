# Правила роботи агента

## Контекст

Це фронтенд s2-dynamicitemgenerator-generator-web. Спілкуйся з власником українською.

- [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) — призначення, предметні правила, межі системи й карта коду. Прочитай перед змінами моделі або генератора.
- [TODO_REFACTOR.md](TODO_REFACTOR.md) — актуальні етапи, обсяг і статус рев'ю.
- [FRONTEND_AUDIT.md](FRONTEND_AUDIT.md) — проблеми F01–F20 та докази.
- [ARCHITECTURE_REVIEW.md](ARCHITECTURE_REVIEW.md) — архітектурні рішення, TypeScript і UI.

Поточні явні вказівки користувача мають пріоритет над цими документами. Наявність плану не є дозволом виконати всі етапи без рев'ю.

## Обов'язкова зупинка після етапу

1. Виконуй лише один погоджений етап TODO_REFACTOR.md за один цикл роботи. Запит «починай рефакторинг» означає перший не виконаний етап; сам по собі він не скасовує зупинок.
2. Якщо попередній етап має статус «очікує рев'ю» або «потрібні правки», не починай наступний без явної вказівки користувача. Запит статусу чи обговорення не вважай погодженням.
3. Усередині погодженого етапу працюй самостійно: реалізація, потрібні перевірки, виправлення власних помилок, оновлення документації.
4. Після виконання критеріїв етапу створи окремий локальний коміт з його кодом, тестами й оновленими пунктами плану. Коміт завершеного погодженого етапу вже дозволений цим робочим процесом; додатковий змістовний дозвіл перед ним не потрібний. Технічні обмеження sandbox виконувати окремо.
5. Встанови статус етапу «очікує рев'ю», повідом SHA, результати перевірок і короткий сценарій ручного огляду. **Заверши відповідь і припини роботу до наступної вказівки користувача.** Не запускай наступний етап, фонову реалізацію, автоматичні продовження чи очікування в циклі.
6. Якщо користувач просить виправлення, залишайся в межах цього етапу. Після перевірок створи окремий follow-up коміт і знову зупинись. Не змінюй уже наданий на рев'ю коміт через amend за замовчуванням.
7. Якщо етап не завершений або перевірка заблокована, чесно зафіксуй причину. Не позначай його виконаним і не переходь далі. Незавершений checkpoint-коміт роби лише за окремою вказівкою.

## Git і ручні правки користувача

- Перед кожним циклом перевір поточну гілку, git status, staged/unstaged diff, останні коміти та актуальний план. Після рев'ю користувач міг змінити файли або зробити власний коміт.
- Робоча гілка рефакторингу — `codex/frontend-refactor`, якщо користувач не вказав іншу. Не перемикай гілку й не створюй нову мовчки при неочікуваному стані.
- Зберігай ручні правки. Не скидай, не переписуй і не коміть чужі зміни автоматично. Якщо вони перетинаються з роботою так, що намір незрозумілий, уточни конкретне місце; незалежні правки не мають блокувати роботу.
- Додавай до коміту лише файли/фрагменти поточного етапу після перегляду diff. Не використовуй бездумно `git add .`, особливо коли є untracked-файли користувача.
- Формат повідомлення: `refactor(stage-N): <конкретний результат>`; для правок рев'ю — `fix(stage-N): <виправлення>`.
- Перевір успіх коміту, його вміст і залишковий git status. SHA повідомляй із фактичного Git-результату, не вигадуй. Статус у плані входить до коміту; власний SHA цього коміту в його ж вміст не записуй.
- Не роби push, merge, rebase, reset, clean, amend або завершення/скасування чужого revert/cherry-pick без відповідної вказівки користувача.

## Межі рефакторингу

- Зберігай семантику `Faction_Class`, категорій і чотирьох рангів гравця. Ваги предметів відносні в межах одного списку й рангу, а не готові відсотки. Не перейменовуй `Newbie` / `ERank::Newbie` на `Novice` у даних чи CFG лише заради термінологічної уніфікації.
- Бекенд s2-loadout-creator-rest та поведінку мережевої взаємодії поки не змінювати. Фронтенд REST/PresetsManager і виклик PAK перевести на TS у межах плану, зберігаючи endpoints, payload, PIN, серверний CRUD пресетів і PAK-пакування; не створювати тестові записи на сервері.
- Основні перевірки виконувати локально через конфігурацію, JSON, CFG і ZIP. Зберігати сумісні точки входу наявних інтеграцій; не заявляти про перевірений PAK/гру на підставі ZIP-тестів.
- Ціль: повністю TypeScript для всього власного програмного коду фронтенд-проєкту, включно з інтеграціями, тестами, скриптами й виконуваними конфігураціями інструментів; strict typecheck має охоплювати їх усі. JS/TS-суміш дозволена лише між етапами. Один власник незалежних baseConfig/config, окремий view, явні функції редагування й генератор без DOM/REST.
- Bootstrap лишається початковою основою. Заміна UI-бібліотеки, новий формат пресетів, localStorage, master/diff та нові ігрові можливості потребують окремої вказівки.
- Не залучай субагентів без явного дозволу користувача. Жодна паралельна робота не повинна продовжуватись під час ручного рев'ю.

## Перевірки та звіт

- Читай актуальні package.json і план: не припускай, що test/typecheck уже існують.
- Для змін коду запускай lint/build та релевантні тести; після впровадження TypeScript — typecheck. Для UI перевіряй відповідний сценарій у браузері; для генерації — зміст CFG/ZIP.
- Для суто документаційних правок достатньо перевірити зміст, посилання й diff. Не запускай весь build без причини.
- Не послаблюй перевірки, щоб приховати дефект. Відомі сторонні помилки відрізняй від нових і зазначай явно; досягнення критеріїв етапу підтверджуй результатами.
- Оновлюй чеклісти TODO_REFACTOR.md лише за фактом реалізації й перевірки. «Реалізовано» не означає «схвалено користувачем».
- Погоджені зміни предметних правил та меж системи записуй у PROJECT_CONTEXT.md; при перенесенні модулів актуалізуй його карту коду. Відрізняй поточні можливості від запланованих; не дублюй там статуси етапів.
- Підсумок етапу: що змінилось; SHA коміту; що перевірено; як перевірити вручну; обмеження/залишкові зміни; статус «очікує рев'ю». Наступний етап до явного продовження не виконувати.
