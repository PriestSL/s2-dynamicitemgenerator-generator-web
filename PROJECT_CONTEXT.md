# Контекст проєкту

Оновлено: 7 жовтня 2026 року. Призначення та предметні правила уточнені власником проєкту; деталі поточної реалізації звірені з кодом. Цей документ зберігає контекст для наступних сесій, а не засвідчує завершення рефакторингу.

## Призначення

`s2-dynamicitemgenerator-generator-web` — візуальний редактор і генератор CFG-файлів налаштування loadouts NPC (НІП) у S.T.A.L.K.E.R. 2. Користувач керує предметами, які отримує НІП при спавні, через форми й таблиці замість ручного редагування довгого конфігураційного файлу.

Користувач може почати з готового пресету, скоригувати налаштування, зберегти їх для подальшого редагування або поділитися своїм пресетом. Фронтенд формує CFG; результат можна завантажити в ZIP або передати бекенду для пакування в PAK.

## Предметна модель

Налаштування списків предметів організовані за такими вимірами:

**`Faction_Class` → категорія предметів → предмет → ваги для чотирьох рангів гравця.**

Це концептуальна схема предметної області, не новий JSON-контракт. Поточний код зберігає списки та параметри у кількох окремих структурах.

| Поняття | Значення |
| --- | --- |
| `Faction_Class` | Поєднання фракції та класу НІП, для якого налаштовується loadout |
| Категорія | Група предметів або пов'язаних параметрів: зброя, пістолети, броня, шоломи, гранати, боєприпаси |
| Предмет | Ігровий предмет зі своїм ідентифікатором; назва в інтерфейсі не повинна довільно змінювати ідентифікатор у CFG |
| Ранг гравця | Один із чотирьох рівнів, для якого задаються окремі значення ваг |
| Вага | Відносна частка предмета серед інших предметів того самого списку для того самого рангу |
| Пресет | Збережене представлення конфігурації редактора, яке можна завантажити та редагувати |

Ранги в описі продукту: **Novice, Experienced, Veteran, Master**. У поточному UI та генераторі перший ранг названо **Newbie**, у CFG використовується `ERank::Newbie`. Порядок поточних rank-масивів: `[Newbie, Experienced, Veteran, Master]`. Рефакторинг не повинен мовчки замінювати ігровий ідентифікатор на `Novice`; зміна видимого підпису — окреме рішення.

### Ваги та ймовірності

Для предмета з вагою `wᵢ` його відносна частка в одному списку й одному ранзі обчислюється як `wᵢ / Σw × 100%`, якщо сума ваг додатна. Наприклад, ваги `1` і `3` дають частки `25%` та `75%`; ваги `10` і `30` задають такий самий розподіл.

- Вага не є готовим відсотком і не зобов'язана бути в межах `0–100` чи складати суму `100` з іншими вагами.
- Не можна змішувати ваги різних списків, категорій або рангів під час обчислення частки.
- Частка в списку не дорівнює безумовній ймовірності отримати предмет у грі: можуть існувати окремі умови та шанси появи відповідної категорії.
- Нульова вага означає нульову частку, коли сума ваг списку додатна. Поведінку порожнього списку або списку з усіма нульовими вагами потрібно явно визначити й перевірити; не показувати `NaN` або вигаданий розподіл.
- Ваги, окремі ймовірності появи, кількість боєприпасів і міцність — різні величини з різними правилами валідації. Їхні одиниці та перетворення слід задавати для конкретного поля.

Це правила моделі редактора. Відповідність фактичної поведінки мода в грі потребує окремої перевірки.

Контракти в `src/model/types.ts` та числові правила в `src/model/values.ts` розрізняють:

| Поля | Одиниця / правило |
| --- | --- |
| WeaponSettings, ArmorSettings, PistolSettings | Чотири скінченні відносні ваги 0–10000; спільна константа MAX_ITEM_WEIGHT у values.ts. Ліміт погоджено власником 7 жовтня; ваги можуть бути дробовими |
| HelmetsSettings, GrenadeSettings.Default.*.chances, PistolSpawnChance | Відсотки 0–100 |
| MinWeaponDurability, MaxWeaponDurability, weapon minCondition/maxCondition | Відсотки 0–100 |
| DropConfigs.nLootChance, nMinDurability, nMaxDurability | Шкала 0–1 |
| AmmoSettings, weapon minAmmo/maxAmmo, grenade minAmmo/maxAmmo | Невід'ємна ціла кількість |
| Пари min/max | min ≤ max; для часткових overrides перевіряти після підстановки успадкованих значень |
| Відсутній weapon override / явний 0 | Відсутнє поле успадковує значення; 0 є заданим числом. Порожній рядок не є значенням моделі |

Правила підключені до локального редагування, повного JSON-імпорту/експорту й генерації CFG. У `generator/loadout.ts` предмети Weapon, Armor і Pistols використовують `Weight`; шанс появи комплекту пістолета використовує `Chance`, як і шоломи та гранати. UI показує вагу й обчислену відносну частку окремо; за нульової суми показує `~0.00%`. `model/effective.ts` обчислює успадковані ammo/condition і переводить відсотки в шкалу CFG 0–1. Індивідуальні параметри діють для основної зброї, стандартної Secondary та пістолетів; відсутній override успадковує значення, явний 0 зберігається.

Наявний `ArmorSpawnSettings.Jemmy_Neutral_Armor.helmetSpawn = true` збережений без зміни defaults/CFG; тип і JSON-валідатор явно допускають спадковий boolean поряд із числовим відсотком. Це виняток сумісності: UI відображає його як 1 і після редагування записує число. Чинний генератор через JS-перетворення трактує `true` як 1%.

## Основні сценарії та результати

1. Відкрити початкову конфігурацію, готовий серверний пресет або локальний JSON.
2. Вибрати `Faction_Class` і категорію, змінити склад списків, ваги за рангами та доступні параметри предметів.
3. Зберегти конфігурацію як JSON або через наявний механізм серверних пресетів.
4. Згенерувати CFG і завантажити ZIP локально або отримати PAK через бекенд.

| Формат | Призначення |
| --- | --- |
| JSON пресету | Дані для відновлення та подальшого редагування конфігурації |
| CFG | Згенеровані ігрові налаштування loadouts |
| ZIP | Локальний архів зі згенерованим CFG та потрібною структурою каталогів |
| PAK | Результат серверного пакування для використання мода |

Поточна реалізація формує один `New_NPC_Loadouts.cfg`. Шлях у ZIP: `Stalker2/Content/GameLite/GameData/ItemGeneratorPrototypes/New_NPC_Loadouts.cfg`. JSON пресету та CFG виконують різні ролі; імпорт згенерованого CFG у редактор не слід вважати наявною можливістю.

## Межа фронтенду й бекенду

Фронтенд відповідає за редагування конфігурації, відображення значень, генерацію CFG та локальний ZIP. Бекенд `s2-loadout-creator-rest` використовується для керування пресетами через REST API та пакування CFG у PAK.

Зараз серверні пресети передають серіалізоване представлення конфігурації редактора через `AppState.exportState()`. Це повний набір конфігураційних полів, а не буквально весь стан інтерфейсу з DOM, відкритими діалогами чи вибраною вкладкою.

Мережеву взаємодію поки не змінюємо. Поточні endpoints, payload, PIN, CRUD і PAK-пакування зберігають свої контракти. Локальні JSON/CFG/ZIP-перевірки дозволяють перевіряти ядро без серверних записів, але не підтверджують роботу PAK у грі.

Погоджена 6 жовтня 2026 року кінцева вимога — повний перехід власного програмного коду цього фронтенд-проєкту на TypeScript, включно з UI, генератором, файлами, REST/PresetsManager, фронтенд-викликом PAK, сумісними фасадами, тестами, допоміжними скриптами й виконуваними конфігураціями інструментів. Усе це має охоплювати strict typecheck. Змішаний JS/TS є лише проміжним станом. Дані, стилі, ресурси, сторонні залежності та згенерований JS не потребують мовної міграції. Окремий бекенд не входить до цієї вимоги; типізація фронтенд-інтеграцій не дозволяє змінювати їхні мережеві контракти.

## Поточна реалізація та заплановані зміни

| Аспект | Зараз | Напрямок розвитку |
| --- | --- | --- |
| Стек | TypeScript у моделі, редагуванні, AppState, генераторі, JSON/ZIP, браузерному збереженні та обробнику завантаження; решта UI й REST/PresetsManager ще JS; Vite, Bootstrap, JSZip | Поетапна повна TS-міграція всього власного програмного коду фронтенд-проєкту |
| Дані редактора | AppState володіє config; локальні зміни проходять validate → normalize → commit. Контролер читає актуальні секції; навігація керується view | Завершення міграції UI та інтеграцій |
| Порівняння з базою | Незмінний baseConfig із defaults, JSON або серверного пресета; метадані, обчислений diff, локальні reset та відновлення видалених предметів | Спільні UI-компоненти порівняння й редагування |
| Серверний пресет | Повне представлення конфігурації | У майбутньому — зміни відносно master-версії пресету; формат ще не визначений |
| Збереження між сесіями | Ручні файли та серверні пресети | localStorage/автозбереження не є погодженою вимогою |

`baseConfig` — незмінний локальний знімок вибраної бази; `config` — поточна редагована конфігурація. Їх можна порівнювати без зміни REST-формату. Майбутнє збереження лише різниці відносно master-пресету — окрема задача: потрібно визначити ідентичність і версію бази, представлення видалень, сумісність та поведінку при оновленні бази. Ці рішення ще не прийняті.

`createEditorState(initial, metadata)` створює незалежні копії бази й робочої конфігурації, незмінні метадані та окремий початковий `view`. AppState завантажує JSON і серверний `data` через спільний `normalizeImport`: після перевірки атомарно встановлює однакові baseConfig/config, зберігає поточний view й оновлює активну категорію. Помилка лишає весь документ незмінним. Завантаження defaults створює нову базу й початковий view; reset до вибраної бази її не замінює.

Повний JSON зберігає 13 наявних полів без метаданих, diff, нової обгортки чи версії. Strict-валідатор перевіряє секції, типи, ранги, одиниці, min/max та посилання на каталоги; лише імпортний адаптер перед ним перетворює підтверджені legacy-форми й числові рядки. Порожнє поле необов'язкового override видаляє його, явний 0 зберігається числом. AppState, модель, порівняння/reset, імпорт і файлові операції перевіряються strict TypeScript. Старі modified*-сеттері збережені для сумісності; PresetsManager при завантаженні вже використовує спільний валідований вхід замість прямих записів.

Звичайне редагування, експорт і генерація не повинні непомітно змінювати базовий знімок. Початкові дані проєкту не слід називати vanilla-даними гри без окремої перевірки.

Погоджені 13 жовтня 2026 року правила порівняння/reset та імпорту:

- Reset працює в поточному контексті категорії/фракції/класу або в окремому глобальному розділі категорії. Діапазони скидаються лише парами min/max зі збереженням відсутніх overrides. Локальний reset рядка не змінює інші списки чи глобальні властивості цього SID.
- Видалені базові предмети відображаються в кінці свого списку приглушеними з позначкою та відновленням. Повторне додавання через Add Item прибирає приглушений рядок; reset активного рядка повертає базові значення. Новий для базового списку предмет позначається як відсутній у базі, його reset видаляє. Порядок предметів не впливає на порівняння, порядок рангів впливає.
- JSON та серверний пресет мають використовувати одну нормалізацію/валідацію й атомарне встановлення незалежних baseConfig/config. Формат серверної обгортки `data` є орієнтиром для відділення конфігурації від метаданих; чинний локальний JSON без обгортки залишається підтримуваним. Фронтенд-завантаження має застосовувати всі 13 полів; мережеві контракти залишаються чинними.
- Legacy-імпорт повинен перетворювати підтверджені старі формати, заповнювати відсутні налаштування з defaults і після обчислення діапазонів застосовувати `min > max → max = min`. Виправлення індивідуального діапазону належить конкретному предмету. Defaults не підставляються замість явних 0/false, відсутнього override чи видаленого предмета у наявному списку. Невідомі/некоректні структури не стають валідними через довільне приведення типів.

Правила реалізовані в спільному імпортері й UI. Частковий reset спершу перевіряє повного кандидата: конфлікт зі зміненими успадкованими налаштуваннями показує помилку без запису й без прихованих змін іншого scope. Поле нового предмета не має власної бази, тому його reset прибирає предмет цілком. [LEGACY_JSON_REVIEW.md](LEGACY_JSON_REVIEW.md) містить аналіз прикладів і межі сумісності. Термін «мастер» у цьому UI означає локальний baseConfig; новий формат master/diff цим не впроваджується.

`generateLoadout(config)` синхронно повертає CFG без DOM/REST і без запису у вхідні дані. Перед генерацією перевіряється повна конфігурація; порожній набір NPC loadouts, відсутні потрібні armor/pistol-комплекти, невідомі предмети стандартної Secondary та непідтримана структура bpatch спричиняють помилку замість некоректного файлу. Secondary лишається з наявних defaults, Guard — із наявним правилом спільних GeneralNPC armor/pistol-комплектів; це не нові можливості редагування.

`generateConfig(state, useRESTPacking = true, name)` зберігає сумісний вибір ZIP/PAK. Ім'я надходить від UI, а CFG один для обох способів. ZIP очікується до завершення; UI показує стан/помилку, блокує повторний запуск і дозволяє повтор після невдачі. `app.js` підключає незмінений `restCalls.js` через типізований транспорт із перевіркою unknown-відповіді. Відомий F15 щодо імені PAK збережено явно: реальний `fileName` перевіряється, але завантаження використовує попереднє fallback-ім'я `<name>.pak`; виправлення серверного workflow відкладене.
