Фронтенд потребує насамперед відновлення коректності редагування, імпорту та генерації. Візуальний рефакторинг сам по собі не усуне найважливіші проблеми: деякі поля не змінюють конфігурацію, різні способи завантаження створюють різний стан, а частина значень неправильно потрапляє у CFG.

Розділення коду на файли вже є, але єдиного контракту між станом, контролерами, UI та генератором немає. Це пояснює конкретні дефекти нижче; встановити, які саме з них виникли через ШІ чи конкретний історичний рефакторинг, поточний аудит не дозволяє.

Рекомендація: залишити Vite, vanilla JS і Bootstrap на першому етапі, виправити втрату даних та додати перевірки критичних сценаріїв. Потребу в іншому UI-фреймворку варто оцінювати після цього, окремим рішенням.

- Переглянуто HTML, усі JS-модулі й стилі, package.json, Dockerfile, Vite/ESLint-конфігурацію та TODO.md.
- Запущено локальний фронтенд і оглянуто інтерфейс у браузері, включно з ширинами 390 та 1440 px.

- Окремими Node-перевірками викликано реальні модулі стану, контролера та генератора. Для перевірки підписів відсотків використано мінімальну підстановку DOM, а не повноцінний браузер.
- Не виконувалися записи, зміни чи видалення серверних пресетів. CRUD із реальним REST, серверне пакування, поведінка готового мода в грі та відповідність актуальним ігровим даним не перевірені.
- Код застосунку та наявний TODO.md не змінювалися. Build створив лише ігнорований Git каталог dist; тимчасові перевірки не додавалися до репозиторію.

Позначення доказовості: **відтворено** — отриманий результат виконання; **за кодом** — простежений конкретний шлях у джерелах; **ризик/рекомендація** — потребує окремого рішення або додаткової перевірки. Це не звіт про навантажувальне тестування чи повний аудит безпеки.

Пріоритети: **P1** — неправильні дані, втрата змін або зламаний основний сценарій; **P2** — надійність, доступність, адаптивність і підтримуваність; **P3** — подальше покращення UX та очищення.

### F01. Зміни атрибутів зброї та броні не потрапляють у стан

**Де:** `src/js/chances.js:344`, `:598`, `:624`, `:640` — `onAttributeChange()` і `fillAttributesTable()`.

Поля отримують `data-to_item` / `data-to_attr`, а обробник читає `dataset.item` / `dataset.attr`. Через це він намагається записати значення у неіснуючий елемент. Окремо checkbox обробляється через `.value`, хоча потрібне булеве `.checked`.

**Наслідок:** зміни боєзапасу/міцності окремої зброї та параметрів броні виглядають введеними, але не застосовуються. У браузерній перевірці Maximum Ammo для GunObrez_SG після переходу Armor → Primary повернувся з 8 до 4. Прямий виклик обробника з dataset, який створює UI, дає `Cannot set properties of undefined`.

**Виправлення:** єдиний контракт ідентифікації поля; окреме зчитування number/checkbox/select; зміна через метод стану, який повертає результат валідації.

**Критерій:** змінене поле зберігається після перемикання категорії, відображається в JSON і впливає на CFG; checkbox експортується як boolean.

### F02. Пістолети відсутні у прив'язці контролера

**Де:** `src/js/state.js:95`, `src/js/chances.js:32`, `:204`, `:321`.

`getChancesSettings()` не повертає `pistol`, але `fillSettings()` очікує його. Сам UI читає `modifiedPistolSettings`, тому таблиця відображається; обробник редагування і Add Item читають `this.settings.pistol`, який дорівнює `undefined`.

**Підтвердження:** після штатної ініціалізації `controller.settings.pistol === undefined`; виклик `onPistolChanceChange()` падає на `GeneralNPC_Neutral`. У браузерній перевірці введене значення також не пережило повторне відкриття категорії.

**Виправлення:** додати пістолети до повного контракту стану, потім прибрати дублювання джерел читання/запису.

**Критерій:** редагування й додавання пістолетів працюють до та після імпорту/завантаження пресета.

### F03. Імпорт JSON розсинхронізує стан, контролер та екран

**Де:** `src/js/events/eventManager.js:232–270`, `src/js/state.js:126`.

Після `importState()` контролер не отримує повторний `fillSettings()`. Нові об'єкти опиняються в AppState, але `settings.weapon`, `settings.armor`, `lists.*` тощо можуть залишитися посиланнями на попередні об'єкти. Окремо пошук активної категорії використовує `data-category` або `textContent`, тоді як категорії — це `<img>` з `id`, без цього атрибута і без тексту. Штатне повторне відображення не викликається.

**Підтвердження:** після імпорту нового WeaponSettings перевірка `controller.settings.weapon !== state.modifiedWeaponSettings` повертає true. Повний файловий діалог імпорту у браузері не проганявся.

**Наслідок:** повідомлення про успішний імпорт не гарантує актуального UI; подальше редагування може змінювати старий об'єкт, який уже не експортується.

**Виправлення:** спільна атомарна операція `applyConfig()` для JSON і пресетів: перевірка → міграція → заміна стану → перебудова похідних даних → одне повторне відображення активного розділу.

**Критерій:** після імпорту нове значення одразу видно; наступна зміна зберігається в тому самому стані, з якого генерується файл.

### F04. Export → Import руйнує поточний формат шоломів

**Де:** `src/js/events/eventManager.js:245`, `:274`; `src/js/configs.js:417`; `src/js/textGenerators.js:59–62`.

Поточний формат — `HelmetsSettings: { HelmetSID: [чотири значення] }`. Імпортер вважає відсутність `Generic_settings` ознакою старої версії та обгортає навіть власний актуальний експорт у `{ Generic_settings: oldVersion }`. Генератор продовжує шукати `HelmetsSettings[HelmetSID]` і не знаходить його.

**Підтвердження:** у згенерованому дефолтному CFG було 66 входжень `EItemGenerationCategory::Head`; після точного відтворення цієї обгортки — 0. Це перевірка тексту генератора, не поведінки гри.

**Виправлення:** прибрати евристичну обгортку для актуального формату. Реальні старі формати підтримувати через явні міграції й зразки старих файлів.

**Критерій:** експорт та повторний імпорт без змін дають еквівалентний стан і той самий зміст CFG, включно із шоломами.

### F05. Серверний пресет застосовується неповністю

**Де:** `src/js/presets/presetsManager.js:395–437`; `src/js/app.js:88–107`.

`_loadPreset()` вручну присвоює частину полів, пропускаючи PistolSettings, PistolSpawnChance, MinWeaponDurability і MaxWeaponDurability, хоча `exportState()` їх зберігає. Прямі присвоєння WeaponList/ArmorSpawnSettings не оновлюють `typeToTable`. Після цього `fillSettings()` оновлює лише частину зв'язків. Крім того, для активної категорії Helmets застосунок шукає `renderHelmets()`, але реальний метод — `renderHelmetSettings()`; контент перед цим уже очищено.

**Наслідок:** завантажений пресет може поєднувати свої параметри з попередніми; списки додавання/редагування використовують старі дані; категорія шоломів може залишитися порожньою.

**Виправлення:** застосовувати пресет через ту саму операцію, що й JSON; використовувати один явний реєстр категорій замість конструювання назви методу.

**Критерій:** усі експортовані поля відновлюються після завантаження, усі категорії залишаються працездатними.

### F06. Edit preset не завантажує конфігурацію редагованого пресета

**Де:** `src/js/presets/presetsManager.js:440–495`, `:612–622`.

Кнопка Edit відкриває метадані вибраної картки. При збереженні відправляється `data: this.state.exportState()` — поточна конфігурація редактора. Попереднього завантаження data саме цього пресета немає.

**Сценарій за кодом:** у редакторі відкритий A → у бібліотеці натиснути Edit на B → змінити лише назву B → Save відправить конфігурацію A як нове data для B. Реальний серверний запис під час аудиту не виконувався.

**Виправлення:** розділити «редагувати метадані» та «замінити конфігурацію поточною»; для другого показувати назву цільового пресета й явне підтвердження. Якщо API вимагає повний об'єкт навіть для метаданих — спочатку отримувати чинні дані B. Не замінювати created часом редагування.

**Критерій:** зміна назви/автора B не змінює його конфігурацію.

### F07. Генератор неправильно застосовує індивідуальні параметри

**Де:** `src/js/textGenerators.js:193–208`, `:413–416`.

Для primary/secondary мінімальна міцність береться з `[weapon].minCondition` — властивості масиву з одним рядком, а не `oWeaponList[weapon].minCondition`. ### F08. Валідація не є бар'єром для некоректних даних

**Де:** `src/js/utils/validation.js:158`; `src/js/chances.js:294–341`; `src/js/renderers/categoryRenderers.js` — обробники міцності; `src/js/fileStreamGenerator.js:6`.

### F09. Ваги, відсотки та ймовірності змішані

**Де:** `src/js/ui/modalManager.js:338–350`, `:427–458`; `src/js/chances.js:444`, `:486`; `src/js/utils/validation.js:70`; `src/js/textGenerators.js:52–55`, `:74`.

Armor Drop показує «0.1=10%», але дозволяє 0–100, і ці числа передаються в CFG без ділення на 100. Шоломи та grenade chances редагуються зі спільним обмеженням 1000, хоча генератор трактує їх як відсотки. Weapon/armor weights нормалізуються відносно суми, тоді як невикористаний `validateWeaponChances()` обмежує кожне значення 100. Дробові поля часто не мають явного `step`.

**Виправлення:** описати три окремі типи: відносна вага, відсоток 0–100, ймовірність 0–1. Визначити одиниці моделі й конвертувати на межі UI/CFG. Порожній override показувати як успадкування із зазначенням ефективного значення.

**Критерій:** введення «10%» дає 0.1 у відповідному полі CFG; вага 200 допускається лише там, де це саме вага; числові межі та step відповідають семантиці поля.

### F10. Lifecycle модальних вікон порушений

**Де:** `src/js/ui/modalManager.js:14–104`; `src/js/utils/dom.js:253–338`; `src/js/presets/presetsManager.js:25`.

`removeMessageBox()` викликає `dispose()` та видаляє DOM без попереднього нормального `hide()` і завершення закриття. **Критерій:** після закриття останнього діалогу немає modal-open/backdrop/блокування scroll; Escape, Cancel та Close дають узгоджений результат; серверна помилка не стирає форму.

### F15. Генерація та REST не мають завершеного UX помилок

- Є legacy-help, дубльовані DOM helper-и, повторення побудови рядків у addRow/fillChancesTable, порожній subscribeToExistingEvents і таймери «дочекатися рендера». Вони ускладнюють визначення справжнього робочого шляху.
- TODO у модалці, TODO.md і текстові заглушки описують різні переліки робіт. Developer Warning показується кожного старту; тексти містять неточності й технічні коментарі замість інструкцій користувачу.

**Виправлення:** чесно позначити доступні можливості й область дії global/faction/Guard; узгодити один backlog; поступово видалити невикористаний код; додати пошук, групування, зрозумілі назви та пояснення успадкування. Реалізацію нових категорій погоджувати окремо.

**Критерій:** користувач розуміє, що змінює і що залишиться стандартним; пошук знаходить предмет за SID/назвою; немає посилань на відсутні методи/модулі в коді, який залишається підтримуваним.

## 4. Що вже варто зберегти

- Невеликий зрозумілий стек без необхідності підтримувати великий UI-framework.
- Відокремлення REST, серіалізації, state, renderers та events уже розпочато.
- Багато місць використовують textContent/createElement, а не динамічний HTML.
- ZIP можна сформувати на клієнті; коректність CFG можна перевіряти без REST.
- Є package-lock.json, production build працює; Bootstrap вже забезпечує придатну основу для форм, таблиць і діалогів.

Ці частини можна використати для поступового виправлення. Повне переписування зараз збільшить площу змін і ризик непомітно змінити ігрову логіку.

## 5. Запропонований план

Оцінки S/M/L нижче — відносний обсяг, не календарні строки. Вони залежать від погоджених вимог до старих пресетів і формату CFG.

| Етап | Обсяг | Робота | Умова завершення |
| --- | --- | --- | --- |
| 0. Зафіксувати контрольні приклади | S–M | Зберегти дефолтний CFG, актуальний JSON та приклади підтримуваних старих пресетів; додати мінімальний запуск тестів і tracked lint-конфіг | Помилки F01–F09 відтворюються цільовими перевірками; відома база для порівняння |
| 1. Відновити правильність даних | M–L | F01–F09, F16: єдина операція застосування конфігурації, типи значень, явні міграції, виправлення генератора, безпечна семантика Edit | Поля змінюють JSON і CFG; round-trip не втрачає дані; імпорт не залишає старих references |
| 2. Стабілізувати дії користувача | M | F10–F11, F15, частина F19: lifecycle модалок, локальний Bootstrap, pending/error/retry, текстові повідомлення без HTML | Локальний редактор працює без CDN; помилки не стирають форму й не лишають заблоковану сторінку |

| 4. Захист роботи та зручність | M | F17, F20: baseline, dirty-state, draft, reset; пошук; пояснення scope/успадкування; очищення legacy | Робота відновлюється, змінені поля видимі, каталог зручний для редагування |

Умови етапу 5 щодо CI та документації доцільно впроваджувати разом із попередніми етапами; перевірка в грі залишається окремим приймальним кроком.

### Пропонована структура після виправлень

1. **Дані:** базові каталоги та defaults, окремо від змін користувача. Не називати наявні defaults «vanilla», поки це не підтверджено порівнянням з ігровими файлами.
2. **Стан:** один ConfigState + окремий UI state (фракція, категорія, відкриті групи). Похідні каталоги не зберігають застарілі посилання.
3. **Контракти:** схема, нормалізація, міграції, правила fallback та одиниці вимірювання в одному місці.
4. **Генератор:** функція `generateLoadout(config)` без module-level mutable settings; окремі функції для effective settings та серіалізації.
5. **Інтерфейс:** спільні компоненти поля/рядка/таблиці/діалогу; явний реєстр категорій; Bootstrap через модульні імпорти.
6. **Операції:** import/export/preset/download повертають узгоджені результати; UI керує pending, error та повторним запуском.

Це можна реалізувати на поточному vanilla JS. JSDoc із перевіркою типів або TypeScript корисні для контрактів, але їх запровадження не повинно затримувати виправлення втрати даних.

## 6. Мінімальний набір приймальних перевірок

- [ ] Атрибути weapon/armor, checkbox і select зберігаються після повторного відображення.
- [ ] Pistols: зміна, додавання та повторне відкриття не дають помилки й змінюють експорт.
- [ ] JSON export → import зберігає всі поля; шоломи присутні у CFG.
- [ ] Після JSON/preset load нові редагування змінюють саме актуальний стан.
- [ ] Серверний пресет відновлює пістолети, глобальну міцність і похідні списки; Helmets не стає порожнім.
- [ ] Редагування метаданих B при відкритому A не замінює конфігурацію B.
- [ ] Нуль, відсутній override та додатне значення мають різні очікувані результати.
- [ ] Невалідний JSON, невідомий SID, неправильна довжина rank-масиву, від'ємні значення та min > max не ушкоджують робочий стан.
- [ ] Нульова сума ваг не показує NaN; числа не змінюють тип після редагування.
- [ ] Закриття діалогу прибирає всі його побічні ефекти; async-помилка зберігає введені дані.
- [ ] ZIP/PAK мають правильні імена та однаковий CFG; timeout і серверна помилка пояснені користувачу.
- [ ] Клавіатура, narrow viewport і 200% zoom дозволяють виконати основний сценарій.
- [ ] Чистий checkout проходить lint/tests/build; REST URL перевіряється і документований.
- [ ] Контрольний PAK перевірений у грі на погодженій версії й наборі сумісних модів.

Тести повинні перевіряти поведінку й вихідний CFG. Snapshot поточного генератора не слід автоматично вважати правильним еталоном: у ньому вже є відомі дефекти.

## 7. Рішення для власника перед реалізацією

- **Обсяг першої ітерації:** рекомендовано відновити редагування/імпорт/генерацію й мінімальні перевірки, потім змінювати вигляд.
- **Базовий пресет:** нинішні defaults чи перевірений vanilla; як версіонувати його разом із версією гри.
- **Overrides:** рекомендовано «порожнє = успадковувати», «0 = явний нуль» з видимим effective value.
- **Формат пресетів:** поки повний snapshot; master/diff/порівняння з TODO.md — наступний окремий етап із правилами зміни бази.
- **Edit preset:** редагування метаданих і заміна конфігурації як дві явні операції.
- **Підтримувані екрани:** повноцінне мобільне редагування чи мінімум доступний перегляд і завантаження; випадкове обрізання контролів треба усунути в обох випадках.
- **Нереалізовані можливості:** що приховати/позначити, а що розробляти — Secondary, Consumables, Artifacts, GuardNPC, сумісність модів.

Жодне з цих рішень і жодне виправлення не застосовані цим аудитом.
